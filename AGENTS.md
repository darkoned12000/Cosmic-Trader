# AGENTS.md -- Cosmic Trader (Flutter)

## Project at a glance

Flutter app targeting Android, iOS, web, Linux, macOS, Windows. Dart SDK ^3.6.2.
The Flutter project lives at the **repo root** (package name `cosmic_trader`).

## Commands (run from the repo root)

| Task | Command |
|------|---------|
| Get dependencies | `flutter pub get` |
| Run (device/emulator) | `flutter run` |
| Run on web | `flutter run -d chrome` |
| Run on Linux | `flutter run -d linux` |
| Analyze / lint | `flutter analyze` |
| Format check | `dart format --set-exit-if-changed lib/ test/` |
| Format fix | `dart format lib/ test/` |
| Run tests | `flutter test` |
| Single test | `flutter test test/widget_test.dart` |
| Clean + rebuild | `flutter clean && flutter pub get && flutter run` |

Always run `flutter pub get` before build, analyze, or test commands.

## Design docs
A design doc moves from the repo root into `docs/` once its work is **complete**. Anything still at
the root is in progress, so the root is the workspace and `docs/` is the archive of finished design
work. When a doc moves, update the pointers to it — `README.md` links and the list below — because
a stale path is worse than no path. Prose citations inside another doc (`§13.1 of
player-avatar.md`) name the document rather than linking it, so those need no change.

**In progress, at the root:**
- `planets.md` — Planet system design (types/atmospheres, colonies, Citadel levels 1-6, homeworld
  NPC repopulation, invasion mechanics, image pools, 6-phase implementation plan). Its "Current
  State" section tracks what has been implemented so far (phase 1 mostly done; colony automation
  and invasion combat outstanding).
- `faction-lore-update.md` — Narrative/lore expansion. Adds a unifying mystery ("The Fracture",
  Cycle 435) to tie the three playable factions into a shared history, replacing the current
  Empire-vs-Mystics-vs-Merchants archetype framing.

**Complete, in `docs/`:**
- `docs/player-avatar.md` — Player avatar system design. **Art direction is settled: portraits are
  generated by a deterministic `CustomPainter`, not drawn as assets** — the original "commission art"
  constraint was reversed on cost grounds, and §2 of the doc records the accepted trade (quality
  ceiling for combinatorial variety and zero asset maintenance) plus the quality bar every visual
  change is held to. Phases 1-4 and 6 are done; the customisation layer is complete (axes,
  backdrops, tabbed editor, per-axis reset, per-axis locks); uploads (phase 5) deferred by choice.
  The standing art bar is higher for NPCs than for the player, because nobody chose their face —
  re-run the sweep after any species-art change.
- `docs/hack-port-update.md` — Hack Port mini-game design (phases 1-3 shipped: security profiles,
  hardened two-stage ports, extraction choices, per-port bans, persistent Hack Codex).
- `docs/cosmic-trader-update.md` — Whole-gameplay review covering mechanics, look & feel, and NPC
  AI; the source of the A2 shared-widget library and A3 look & feel waves.

Layered structure under `lib/`. Screens import storage directly (no repository/DI layer).

      combat_service.dart         -- combat resolution engine, damage/loot/faction-standing calculation, siege estimate, CombatOutcome contract, morale (trigger/eligibility/resolution)
      port_combat_service.dart    -- port combat resolution engine (shared siege core) with defense stats

### Universe generator algorithm

`UniverseGenerator.generate()` runs 8 phases:

1. **Init** — Greek/mythological sector names, placeholder coords, empty warp lists. Also generates NPC ships via `_createNpcs()`
2. **Terra Prime** — Sector 1 gets a Federal port with random pricing via `_createPort`
3. **NavHaz/Anomaly** — 15% navHaz + anomalies at `anomalyDensity` outside FedSpace
4. **FedSpace hub** — Sectors 1-7 connect 2-3 peers; 8..fedEnd connect to 2-3 hubs
5. **General warps** — "grow-from-center" coords with bubble clustering; distance-weighted connections
6. **Orphan/connectivity/balancing** — Fix orphans, BFS repair, `_balanceDistribution` up to 100 iterations
7. **Ports** — FedSpace = Federal; outside = portDensity (30% federal, 40% free, 30% independent). Type strings are generated dynamically for the number of configured commodities. Each port gets defenseLevel (0-4), portCredits, ~40% chance of NPC owner; hardware emporium flag at hardwareEmporiumDensity
8. **Planets/NPCs** — Planet placement at planetDensity with per-type GIF images; a homeworld per major faction (duran/vinari/trader — preferred types, unique names, NPC spawn fields); NPCs by per-faction density settings (trader/duran/vinari/pirate). Aliens are not currently generated (only producer comments + a lore mention reference them)

Seeding: `GameSettings.seed` → `Random(seed)`. Seed 0 → time-based replacement.

### Economy model

Data-driven commodity system via `CommodityConfig` + `CommodityRegistry` (single source of truth in `commodity.dart`).
Adding a commodity requires just 2 entries in `commodity.dart` (+ mirror in `defaultsMap`).

Eight goods: minerals, organics, industrial, food, ore, crystalline, munitions, contraband.
Each commodity has a `[priceMin, priceMax]` range split at the mid-point (`splitPoint`):
- **Sell price** (player buys from port) = random in `[priceMin, splitPoint)` — lower half
- **Buy price** (player sells to port) = random in `[splitPoint, priceMax]` — upper half

Base prices **guarantee** `maxSellPrice < minBuyPrice`, but live effective prices layer cash-ratio × supply/demand depth × drift × regional/anomaly × standing (capped [0.25, 4.0] on the multiplier), so near-split routes can invert into real (logged, self-correcting) losses.

Ports use dynamic type strings (N characters, one per commodity). Each character = `S` (port sells, player buys), `B` (port buys, player sells), or `X` (untraded — contraband at law-abiding ports, padding on old saves). Generated at port-creation time with at least one `S` and one `B` among legal goods.

A port never buys and sells the same commodity. Contraband trades only at free/independent black-market ports (~30%).

Current defaults (editable in the Settings → Commodity Economy section):
- Minerals: 10-75 cr, 10,000-80,000 qty
- Organics: 80-150 cr, 5,000-70,000 qty
- Industrial: 160-300 cr, 3,000-60,000 qty
- Food: 5-40 cr, 8,000-60,000 qty
- Ore: 30-120 cr, 6,000-50,000 qty
- Crystalline: 200-450 cr, 1,000-8,000 qty
- Munitions: 150-400 cr, 2,000-15,000 qty
- Contraband: 300-800 cr, 500-5,000 qty

### NPC AI engine

Autonomous NPCs with 12 personality archetypes (3 per faction) across 4 factions (Duran, Vinari, Trader, Pirate). Goal state machine with weighted random selection (null-instantiating picks are skipped, not stalling):

- **Goals**: tradeRoute (incl. sell-first for full/nib holds), explore, attack, bankDeposit, bankWithdraw, patrol (5-leg expiry), flee, upgradeEquipment (repairs + levels + arrays), raidPort (siege-gated), refuelEnergy (discovered emporiums only), buyPort
- **Guards**: banking/distress/refuel only preempt interruptible (explore/patrol/none) goals; refuel breaks committed legs below 10%; dead goals never steer movement; failed routes cool 5 min
- **Personality config**: aggression (0-1), greed (0-1), caution (0-1), explorationDrive, maxTravelDistance
- **Pathfinding**: BFS shortest path via `PathfindingService` (id-keyed)
- **Trading**: Port discovery, profit-per-hop route evaluation (affordability + cooldown + standing aware), buy/sell commodities, bank profits
- **Banking**: Autonomous deposit/withdraw based on caution thresholds and credit balances; Guild interest for NPCs and players
- **Combat**: NPCs hunt hostiles (greedy prefer bounties), raid beaten ports, attack players (aggression + power + fear/hatred calculus)
- **Fear/hatred**: Notoriety inflates perceived power (deterrence + sector-clearing); standing ≤ −50 substitutes for hostility at 1.5× odds
- **Distress signals**: Outmatched NPCs broadcast; max 3 armed responders with trip budgets; en-route revalidation
- **Port owners**: NPCs buy unowned ports, collect revenue, upgrade defenses/storage; ownership keyed by stable id
- **Death cries**: Faction-specific broadcasts when NPCs are destroyed
- **Repopulation**: Homeworld control-gated respawns (extinction reversible)
- **Processing**: `GameTickService` (adjustable interval, re-entrancy guard, per-NPC error bulkhead, Fed bounties, NPC interest) batches NPC turns, proximity-filters events to player sectors

## Economy notes

The buy/sell price model creates a guaranteed profitable spread at every port — sell prices (player buys) are always in `[priceMin, splitPoint)` and buy prices (player receives) in `[splitPoint, priceMax]`. With current defaults (minerals 10-75, organics 80-150, industrial 160-300), a typical trade run nets 30-300%+ return. Players can also edit every range (price and quantity) in Settings → Commodity Economy.

- **Painter split into a `SpeciesArt` seam** — `avatar_portrait_painter.dart` went 1507 → 187 lines (orchestration only). `avatar_species_art.dart` holds `AvatarDrawContext` (one argument instead of a fifteen-parameter call) plus the four required slots `appendages` / `headPath` / `faceTexture` / `outfit` and the shared eyes/expression/head-shading; the three species live in their own files. - **Terran male faces fixed** — all three presentations previously shared one rounded skull and thin high brows, so the male faces read girlish. The player's `eyes` choice is still honoured; only lid weight and skull/brow geometry bend.
- **Decoupled colour axes** — `AvatarStyle` gained five nullable slots: `hairColor`, `eyeColor`, `markingColor`, `trimColor`, `gear`. Before these, `hair` chose a silhouette *and* its colour together, so 3 options gave 3 looks instead of 9. `null` means "keep the colour the shape implied" and resolves through `AvatarPalette.legacyHair` / `legacyEye` / `legacyMarkingPigment` / `outfitTrim` / `AvatarStyle.effectiveGear`, which reproduce the old shape-keyed behaviour exactly — so pre-existing saves render byte-identical and a coupled style writes no new JSON keys. Out-of-range values coerce to `null` rather than clamping, so a corrupt save falls back to the shape's own colour instead of snapping to an end of the list. `copyWith` needs explicit `clearHairColor` / `clearEyeColor` / … flags because `?? this.x` cannot clear a nullable slot. `isCoupled` reports whether anything is overridden; re-rolls leave each slot null ~1 roll in 4 so coupled looks stay reachable.
- **Rendered-pixel regression guard** — `test/avatar_outfit_render_test.dart` samples the rendered torso band and asserts a multi-tone garment was drawn. It exists because a refactor once wrapped already-pixel values (`shoulderTop`) in `uy()` a second time, pushing every garment off-canvas: no exception, and all 380 tests passed while the Duran lost their armour, the Vinari their shroud, and the Traders their collar. Verified by re-injecting the scale bug. **Exception-only assertions cannot catch off-canvas drawing.** The file is deliberately standalone — `Picture.toImage` never completes inside the fake-async zone `testWidgets` runs in, and hangs if mixed with widget tests in the same file.
- **Backdrop axis** — `AvatarStyle.backdrop: int?`, the sixth nullable slot. Nine per-species options (Duran forge glow / ember field / void, Vinari aurora / nebula / deep drift, Terran hangar / starfield / viewport), implemented as a `SpeciesArt` slot so each species owns its environment like it owns its anatomy: `backdrop` dispatches `null` → `factionBloom` (the original single backdrop, byte-identical for pre-axis saves) or `backdropVariant(c, index)`, which defaults back to the bloom so an un-art-directed index still renders something. Two defects caught only by rendering: the first planet limb was bright enough to become the most luminous thing in frame and pull the eye off the face, and wide-halo bright stars clumped into a lens-flare column.
- **Draw order is part of the avatar save format.** `AvatarDrawContext.rng` is a *single shared* sequence — the Vinari drift motes and the Terran hair lean consume from it. Taking draws from `rng` there would shift every later consumer and silently repaint every portrait saved before the axis existed — the exact failure `null`-means-legacy exists to prevent.
- **Vinari silhouette axis (`player-avatar.md` §13.1)** — the NPC sweep's biggest finding, now fixed. `hair` became a silhouette axis: crown of light (plain, matching the Duran "low ridge" and Terran "close-cropped"), tendril fall (seven bowed tapered tendrils with glowing tips), and frill fan (a ribbed crescent membrane with a blooming lit edge, tapering to a point at each temple). Repurposing `hair` rather than adding an axis avoided an enum value, a nullable slot, a serializer, palette work, and catalog wiring. Four defects were render-only: the frill had a flat cut bottom, the frill never cleared the crown (the cubic-apex bug above, which also hid its ribs and rim), and a translucent membrane is *darker* than the head behind it so the frill read as a monk's cowl — it is now three stacked passes (bloom, membrane, lit rim), because light has to be added for it to read as light. - **A guard that cannot fail is worse than no guard.** `test/avatar_outfit_render_test.dart` has six pixel-sampling guards, each verified by injecting the fault it exists to catch: multi-tone torso (garment off-canvas), backdrops distinct and none-is-the-bloom (an index falling through to the default case), appendages-outside-the-head-clip (the original layer-order bug, re-injected by moving `appendages` back inside `clipPath`), the two-part Vinari silhouette guard described above (re-injected twice — once with the axis made inert, once with the frill's apex pushed back below the crown), and the per-species scowl floor (re-injected three ways — with the Terran override ignoring the Scowl, with the scowl disabled globally, and with the mouth curve flattened). When comparing renders, hold the *style* constant and vary only the axis under test, or the comparison silently tests something else.
- **Widget tests have two measurement traps.** (1) The default test font renders every glyph as a full-width box, so text measures ~2× too wide — an assertion that the six-tab editor strip fits a 430px phone "failed" by 90px and looked like a real layout bug; `test/avatar_designer_test.dart` loads the bundled `Audiowide.ttf` with `FontLoader` (inside `tester.runAsync`, or the load never completes) before asserting anything about fit. (2) `setSurfaceSize` does **not** change `view.physicalSize`, which still reports the binding's 800×600 at dpr 3, so `expect(rect.right, lessThanOrEqualTo(view.physicalSize.width / dpr))` passes no matter how far the row overflows — measure against a rendered widget's rect. Related: **a tap on an off-screen widget silently does nothing** in `flutter_test` (it warns and moves on), so a test that taps a tab must assert the *content* changed, or scroll the target into view first.
- **Derive option counts from the list that supplies them, never from a shared constant.** `AvatarStyle.toneCount` is 6, but every dye list and the garment list hold 3. Generating colour options by looping to `toneCount` threw a `RangeError` *while building the row*, so the Face tab rendered one axis and then nothing — invisible to every test, found only by screenshotting the editor. `test/avatar_axis_catalog_test.dart` pins each axis's count against its source for the same reason.
- **`AvatarStyle.copyWith` cannot clear a nullable slot.** It resolves `?? this.x`, so `copyWith(eyeColor: null)` keeps the old value. Any "return this axis to its seed" path must use the explicit `clearEyeColor` / `clearBackdrop` / … flags, or the Reset button silently does nothing on every colour slot (whose seeds are all `null`).
- **Per-axis locks are transient by design and must stay out of the schema.** They describe how a player wants to re-roll, not what their pilot is, and are spent at Save. `AxisStyleAxis` lives in `lib/data/models/avatar_selection.dart` rather than beside the editor UI so `AvatarStyle.rerolled` can honour locks without the data layer importing widgets. `rerolled` rolls from the **current** style, not from neutral, because a lock has nothing to hold otherwise — with no locks the two are indistinguishable. `test/avatar_selection_test.dart` asserts the style's JSON stays a flat set of ints with no lock key.
- **Never assert a random outcome in a test.** "After a random re-roll this axis should differ from its seed" is true 3 times in 4 for a 3-option axis, and produced three separate flaky tests. Use a **forced generator** — `int nextInt(int max) => max - 1` against a base whose every axis is `0` — so anything that gets rolled is guaranteed to differ. Also note `pumpWidget` with an identical widget tree **reuses the existing `State`**, so a test asserting "this does not survive reopening" must pump something else in between to actually destroy it.
- **A layout that collapses does not overflow, and nothing will tell you.** Adding a 28px portrait to the faction-rankings Top 10 row squeezed the name column to ~4px at 430px width. `Expanded` absorbed the shortfall, so there was no `RenderFlex` overflow and no test failed — but every name then rendered one character per line and each card grew to ~200px. Only a 430px screenshot showed it. The guard **measures** instead: the name `Text` must be >80px wide *and* <40px tall, and the height is the half that matters, because a collapsed column is a *wrapping*, not an overflow. Use a deliberately long name in the fixture — a short one survives the squeeze by luck. Fixed with a `LayoutBuilder` fallback to one column.
- **A missing `path_provider` in a widget test hangs; it does not throw.** Driving `FactionRankingsScreen` needed `PlayerStorage`/`NpcStorage` fakes (both constructors were private, so a subclass could not be declared at all) and a `BountyBoard` whose `ensureLoaded` awaits `BountyStorage`. That await is left **pending** inside the fake-async zone, so the screen sat on its spinner forever and the test passed with nothing rendered. `BountyBoard.skipDiskLoadForTest` exists for exactly this. Whenever a screen loads in `initState`, check what it awaits before assuming a fake is enough.
- **Re-read your own edit; a fix can quote numbers for code you did not write.** A pirate-trim fix aimed at contrast against the *pirate's own cloth* kept `final base = outfit(species, variant)` — which resolves at the **default native affiliation**. The pirate branch therefore computed exactly what the native branch computed, and pirate trim came out **bit-for-bit identical** to native trim. The comment described a derivation the code did not do, the "never brighter" assertion passed because it was `lessThanOrEqualTo` and they were *equal*, and the render looked fine. A peer review spotted the assertion's weakness; re-reading my own edit found the cause. A described fix is not a checked fix: after any change, read the line you believe you changed.
- **Assert the property a viewer can see, not a relationship between two values from the same input.** A trim-vs-trim comparison cannot detect a trim that is invisible on its own cloth, and it cannot detect a trim that never varied at all. Both need their own assertion, and the second needs a *strict* inequality — `lessThanOrEqualTo` let "identical" through. The weak assertions were kept alongside the strong ones because they still catch a sign flip, and the comment now says exactly which failure each one is for.
- **A confounded measurement may be unable to see the thing it is named after.** The scowl guard compared a pirate face to a native one, which also picks up cloth, hair dye, and a Vinari face wash drawn in the hair colour: the Vinari's *background* difference was 3736 pixels against a scowl contribution of ~95, so an entire scowl removed from the Vinari still read far above the floor. The comment pointed at another file for cover — but that file asserts properties of a value object and never renders, so it could not tell whether a species' `expression()` consumed it. **A gap documented as covered is worse than an open one.** Fixed with an `AvatarDrawContext.scowlOverride` seam: render the same pirate twice, once with the scowl forced off, so the confound disappears for all three species (the smallest measurement rose from "unmeasurable" to 184).
- **Never `git checkout` inside a fault-injection loop.** Restoring a file with `git checkout` after injecting a fault reverts it to the last *commit* — silently discarding days of uncommitted work. It nearly did. Back the file up to `/tmp` first, restore from that, and assert the injection landed. Silent no-op injections have bitten three times now; the assert is not optional.
- **A count of distinct colours measures smoothness unless you quantise it.** "More than 8 distinct torso colours" was being satisfied partly by anti-aliased edges. Re-measuring with channels bucketed to 16 levels gave the real distribution — Duran 10-12, Vinari 8, Terran 6-7, **flat fill 1** — and showed the old threshold sat *below* the real Terran value, so it had been measuring the renderer, not the art. Quantisation is now opt-in per call, because the backdrop guard compares smooth gradients and a global change collided two options outright.
- **A test named after an invariant it does not touch is decoration.** "is not persisted on a selection" asserted `style == null`, which is true whether or not an affiliation field exists — Dart offers no runtime way to assert a field is absent. It now checks the serialised key set, which can see one; the real guard for absence is the type system refusing to compile. Likewise, a loop over species and presentation claimed to prove independence from both in a function whose signature takes neither.
- **A lazy list makes a content assertion lie.** The Planet Guide is a `ListView`, so it builds lazily. Adding one section pushed the cards below a 2400px test viewport out of the tree, and six content tests began reporting text as *missing* when it was plainly on screen. A find that returns nothing on a lazily-built list means **not built**, not *not there* — size the viewport or scroll. This is the widget-test twin of "a tap on an off-screen widget silently does nothing".
- **A `ListView` in a test needs a deliberately tall viewport, and the comment has to say why.** Otherwise the next person shrinks it back to something reasonable and every content assertion fails for a reason that has nothing to do with the content.
- **A correct balance can be unreachable, and the UI is what makes it live.** Ports already had the right sink — finite `maxDemand` per commodity, refilling over 24h, with `effectiveMaxDemand = maxDemand x 1.5^storageLevel` so a storage upgrade opens up the market. Measured: ~1.24M minerals/day of demand across a 100-sector galaxy, i.e. a real ceiling on converting a colony into credits. But buy/sell moved **one unit per tap**, so cashing in 78,000 minerals took 78,000 clicks. The economy read as broken rather than throttled, and a colony's shipment pool was effectively uncashable. Fix the tap size, not the balance. When a player says a number is too generous, measure the sink *and check it is reachable through the UI* before nerfing production.
- **A rate the screen displays is a promise, not decoration.** The planet screen showed `1,200 -> 1,440/tick` per track and nothing ever applied it: the only code writing a planet's stores was the credits-based transfer in the same file. A displayed feature that silently does nothing is **worse than an absent one**, because it looks like a working one. Fix: `Planet.produce()` as the single source, read by both the tick and the screen, plus a test asserting `produce()` adds exactly what the display getters report. The display originally inlined the formula four separate times, so the two could not have been checked against each other even in principle.
- **A percentage penalty applied to the *remaining* population is asymptotic, and "2% per tick kills you in 50 ticks" is wrong.** The starvation bleed floors to 0 below 50 colonists, so a starving colony shrank to 49 and then stopped losing anyone — a permanent zombie world, unrevivable by delivering food because the tick had nothing left to take. A cap needs an explicit floor of 1. Because the bleed compounds, the real figures are: from 10,000 colonists, 10% gone in 3 minutes, half in 17, zero at ~170. Measure the curve, then write it in the comment; the number I guessed into the source was wrong by 6x.
- **Two natural-width `Text`s in a `Row` overflow as soon as a value gets long, and it is invisible until you render.** Three instances, all pre-existing, all found by rendering the planet screen at 430px: `_infoRow` (broke the moment Population was shown against its cap), the shared `StatBar` stacked layout (app-wide, not just that screen), and the "Owned by" faction header (153px over). Neither reading the code nor `flutter analyze` finds them. Two card rows also sat side-by-side inside two `Expanded` halves of a 430px phone; fixed with a `LayoutBuilder` column fallback below 560px, the same pattern the faction rankings screen uses.
- **An ellipsis that stops an overflow can still leave content unreadable — fix the cause.** Making `StatBar` ellipsise removed the overflow but truncated a player's own stored resources to nothing at phone width. Flexing the text was the symptom fix; stacking the two cards was the cause fix. Both were needed.
- **A parameter with two units, and a `max(1, …)` that hides it.** `lidWidth` returned **pixels** in the base class and a **raw fraction** in the Terran override, and the caller clamped with `math.max(1, lidWidth(c))`. Both Terran presentations therefore drew a 1px lid, so the male squint — one of the three documented changes that stop the male faces looking girlish — was **never rendered at all**. Renamed to `lidFraction` with the `c.u()` applied at the single call site. When a hook is overridable, its unit belongs in the name, and any `max(1, x)` on a size is worth suspecting: it turns "too small to see" into "silently absent".
- **A brow is a V: `side` belongs in the x term only.** The tilt was multiplied by `side` in the y-offsets as well, so the left brow's inner end rose while the right brow's fell and the pair ran as a **diagonal** — a head tilt, not a frown. This is very likely why a native "Stern" read as *unimpressed* and why the scowl needed a `browBias` big enough to fight the shape. Fixed for pirates (`ySign = scowl.isNone ? side : 1.0`), which is what the same gating buys elsewhere: a new feature gets the correct geometry for free while saved portraits keep the old shape.
- **A slot can be correct about clipping and still be in the wrong place.** Terran gear was called from `appendages` with a comment insisting it "must be unclipped" — true, and irrelevant, because `appendages` is painted *before* the head fill. Every part of the goggles and headset inside the skull was painted over; only the earcup showed, so two of three gear options were indistinguishable. That forced a new `SpeciesArt.accessories` slot, drawn last and unclipped. The general rule: `appendages` is behind the head **on purpose**, so anything crossing the skull's *interior* needs its own slot — the seam had no home for worn things that overlap the head.
- **A fixed colour table cannot serve six tones.** Measured across every species' own pigment table, the worst pigment-on-skin pair is **1.02:1** — drawn, and completely invisible. `markingPigment` now takes the skin and nudges a **pirate's** mark away from it until it clears 1.5:1 (lighten or darken, whichever moves further). Natives keep the authored table so no saved portrait moves; the same weakness is real for them and is separate work, because fixing it repaints every portrait that has markings.
- **Pin a list you use as a modulus.** Pirate species came from `AvatarSpecies.values.length`, so adding a fourth species would reshuffle every existing pirate's body in one release — new faces for NPCs nobody touched, with no diff pointing at it. Replaced with an explicit `const _pirateSpecies` list, so a new species is a deliberate edit here.
- **One geometry, one source.** A peer review found four separate Vinari frill defects that all came from the frill **re-deriving its own curve** in each place that needed it: a constant documented as head radii but used as pixels, a closed path that `drawPath` therefore stroked its closing chord on, rib endpoints sampled from a quadratic that only reaches halfway to its control (so they landed below the crown, behind the skull), and a tendril angle read from +x instead of straight-down (so `cos` never went negative and every strand leaned right). Rendering missed all four because each was locally plausible. Fixed by a single `_FrillArch` holder that the fill, both strokes, and the rib endpoints all come from. If geometry is needed in more than one place, write it once.
- **Measure a shape where nothing else can reach.** Rebuilding that guard took three attempts and the failures are the lesson. (1) Widening the sample band silently blinded it, because `coverage.reduce(max)` only catches a fault in whichever form is *tallest*. (2) Counting brightness cannot work in a wide band — the head is identical across forms and dominates; the input moved under 7% when the defect itself was reintroduced. (3) **`crest()` also varies with the axis under test** and supplied 4500 of 5709 differing pixels, so the guard vouched for an entirely inert axis. The mask has to be *outside the head silhouette*, and the guard must **difference** each form against the plain one.
- **Two shapes of "wrong" need two different assertions.** A silhouette can vanish (caught by a pixel count) or be lopsided (**not** caught by one: the one-sided tendril spray covered 1600px against the symmetric fall's 1129, so every size threshold passed it). Lopsidedness needs a left/right balance check, and it is the one that caught a real direction bug.
- **A doc comment attaches to the next declaration, and an inserted class steals it.** Adding `Scowl` between the `SpeciesArt` doc block and `SpeciesArt` — with no blank line — made Dartdoc attach the whole run-on comment to `Scowl` and left `SpeciesArt` undocumented. The layer order is the invariant that has already been broken once; a doc that does not attach to its class is worth checking with `grep -n` after inserting anything above a declaration.
- **A derived value can guarantee the wrong property.** Pirate trim lerped the *native* trim toward black so "darker than native trim" held by construction — and the test asserted exactly that — while contrast against its own garment sat at 1.15:1, worse than the native 1.43:1 in all nine combinations. It was optimising for its own assertion. Deriving from the pirate's own cloth holds **both**. When a value is derived, ask which property a viewer would notice, and assert that one.
- **Assert a rate on both sides, and check the slot is actually reachable.** Pirates carry markings ~95% of the time against ~76% for natives, asserted from both sides. But with `hairColor` null the pirate dye resolved off the hair *shape*, so a pirate got 3 looks from a 3×3 grid — the exact coupling the dye axis exists to remove — and one entry of each pirate dye list was unreachable. Biasing or varying a slot does nothing if nothing reads it.
- **Never suppress an option and call the result "done" — look at it.** Pirates were meant to stop smiling, so the smiling expression was simply never generated. Rendered side by side that was *technically correct and visually wrong*: a native "Stern" reads as *unimpressed* and "Neutral" as *calm*, and neither is mean. Pirates now get a `Scowl` on **every** expression — brow bias, a deeper arch, the brow lifted toward the eye, a mouth that is always a downturn (−0.16 neutral, −0.30 stern), wider and heavier so it holds at 48px. - **A species that overrides a shared method silently opts out of everything in it.** `Scowl` is consumed in the base `expression()`, and `TerranArt` overrides that method *without calling `super`* — so the first implementation left the one species whose face actually shows a mouth never scowling. When an override duplicates shared behaviour rather than extending it, put the shared decision in a **value** (`Scowl.forContext(c)`) that each implementation consumes explicitly, not in code only one of them can reach.
- **"These two renders differ" cannot detect a difference being *removed*.** The obvious guard for the scowl — "a pirate face differs from a native one" — passes with the scowl entirely deleted, because the cloth, hair dye, and backdrop differ too. Verified by disabling the scowl and watching the test pass. This is the mirror image of the Vinari frill trap: that guard could not see a difference that *should* exist, this one could not see one that *should not*. The fix is a **floor** on how many pixels the feature must contribute, measured where nothing else can reach — a strip strictly inside the head, so the backdrop is occluded and only skin and features remain. Measured with/without: Duran 4 → 492, Terran 0 → 713. A per-species pixel *count* is what makes this work; the boolean cannot. Where a floor cannot separate (the Vinari's face texture already differs by 3736 px because it is drawn in the hair colour), assert the underlying **value** directly instead and say so in the comment.
- **Pirates are an affiliation, not a species (`player-avatar.md` §13.2).** A fourth `AvatarSpecies` was the obvious fix for pirates sharing the human pool, and would have been wrong twice over: they are defectors, not a race, so a pirate Duran is still scaled and horned — and one species would have collapsed a mixture of three silhouettes into a single one. `AvatarAffiliation { native, pirate }` sits on `AvatarPortrait` orthogonal to species and changes only cloth, ring, and marking frequency. Never persisted (pirates are not selectable, so it only ever appears on a derived NPC portrait). A hidden control must not start working behind the player's back.
- **Assert a rate on both sides.** The pirate marking bias measures ~95% marked against ~76% native, and the test fails both below 90% **and** at 100%. An earlier version re-rolled every unmarked pirate and measured exactly 100% — a stronger claim than "more often", and it threw away a variant for nothing (a pirate with no marks reads as somebody who joined last week).
- **Assert darkness with relative luminance, not by eye.** Two hand-authored "darker" values were wrong: pirate trim came out *brighter* than native Duran trim, because the Duran's issued armour is already nearly black. Pirate trim is now derived (the native trim pushed 42% toward black) so "darker" holds by construction for every species and variant. And "darker hair at every index" is simply false — a pirate is bleached as often as they are sun-darkened — so that one asserts the per-species *mean*.
- **NPC portraits: the standing rule.** The NPC art bar is **higher** than the player's, because nobody chose the face, so *every* combination must hold. A 48-face-per-faction sweep found three defects no test would have: Duran horns inheriting the skin tone into a bone-coloured plume, the Terran "short spikes" reading as a crown, and the Vinari varying far less than the other species. The first two were invisible in the 27 seeded looks, because no seed paired the offending tone with the offending shape. **Re-run a sweep after any species-art change.**
- **Repurpose a slot before adding an axis.** The Vinari variety fix cost no schema change: `hair` was already the Vinari's head-feature slot and was simply inert, so it was made a silhouette axis (crown of light / tendril fall / frill fan). A new axis would have needed an enum value, a nullable slot, a serializer, palette entries, and axis-catalog wiring to say the same thing. Check whether a slot is already doing nothing before adding a fourteenth. The same instinct applies sideways: check whether a new *enum* is warranted before adding one — the pirate fix needed a new concept but no new species.
- **"The renders differ" is not "the silhouette changed."** The Vinari frill's arch put its *control points* at the requested apex, and a cubic's midpoint only reaches 3/4 of the way to its controls — so a requested 2.16r apex peaked at 1.62r, below the 1.46r crown, and the whole membrane hid behind the skull. It still rendered *differently*, because the wide bloom leaked upward, so a difference assertion passed while the defect was fully present. The guard in `test/avatar_outfit_render_test.dart` therefore has two parts, and both were verified by re-injecting their fault: the forms must differ above the crown, **and** at least one form must cover ≥30% of the above-crown band above a luminance floor (measured 51% correct vs 12% faulted). Route curves through explicit apex points rather than control heights whenever the height is the point.
